# B15b DRAFT (2026-10-24): a compiled map for the B15 constructor stage

**Status: DRAFT. Not registered.** It goes to the Bridge for review and then to the user for an OK. No counted B15 run
uses a compiled map until this text, amended by that review, is in PREREG_chaos_horseshoe_phase2.md and the gates
below have passed.

## Why

The Python B15 (MNFlow, scipy DOP853) built 26,047 W^u arc points in 300,804 s, about 11.5 s per arc point. It is
not relaunched after the macOS 27.0.1 update (the user's decision). The compiled maps take about 4.5 ms per call,
with the Jacobian, near the saddle.

## What changes, and what does not

- **Changes:** only the implementation of P, Pinv and py_of that the frozen B14 constructor calls through
  `mn_numerics.plug_into_constructor`. The adapter is `kerr_compiled.CompiledFlow`, which keeps MNFlow's signatures
  and return conventions.
- **Unchanged:**
  - hs_construct.py;
  - every B14 and B15 threshold (eps 1e-4, K 5, dmax 0.01, min angle 0.01, the θ_floor red flag);
  - TMAX = 1e6;
  - the seed;
  - the step logic, and the registered prediction;
  - pcache journalling.
- **Primary implementation:** `kerr_rs` (Rust).
  - Field: `mn_field.rs`, generated by mn_codegen_rs.py from the same sympy source and CSE as gen/mn_field.h.
  - Jacobian: forward-mode dual numbers.
  - Integrator: its own Dormand–Prince 5(4) with Hairer's dense output.
  - Events: bisection on the dense output to |dt| ≤ 1e-14 (1 + t).
  - Tolerances: rtol = atol = 1e-12.
- **Second implementation:** `kerr_p.cpp`. It has the same field and C ABI, uses Boost.Odeint DOPRI5 with a
  different error norm, and is used only for cross-checks.
- **Reference:** MNFlow, the map B15 was registered with.

## Disclosure: a bug in kerr_p.cpp, found by the second implementation

As committed in 18c33e0, kerr_p.cpp's slide-back correction ran in place. The i = 1 iteration zeroed V[1] before the
p_x and p_y rows used it. The section derivative's p_x row was therefore uncorrected:

- det DP came out 0.57–0.61 instead of 1;
- the DP entries were off by up to 1.3e-2 relative;
- the x row was unaffected.

The Rust port copies the y row first. On the same points it matched central finite differences of its own P to about
1e-8, with det DP = 1.000000. After the same fix in kerr_p.cpp, the two compiled maps agree on DP to 7.9e-13 at
200 points. **No counted result ever used kerr_p's DP:** its gate had not finished, and the earlier B15 used MNFlow,
whose numpy outer product is correct (its step-1 eigenvalues multiply to 1).

## Gates (all must pass before a counted run; criteria fixed here, before the gate outputs are read)

**G1. Against MNFlow.**

- Run: `kerr_p_gate.py 12 2000 <lib>`, for kerr_rs and for the fixed kerr_p.
- Points: 12 points, seed 20261024, at perturbations of 1e-6 to 1e-3 around z* = (1.8411884397812655, 0).
- Criterion: max relative difference ≤ 1e-10 in py, P, T, DP and Pinv. Any return mismatch is a FAIL.
- Note: the gate run started on 2026-10-24 uses the unfixed kerr_p.dylib, which was loaded before the fix. Its result
  is a demonstration of the bug, not G1.

**G2. Cross-implementation.**

- Run: `kerr_rs_cross.py 200 2000 1`.
- Criterion: ≤ 1e-10 in every quantity, with 0 mismatches.
- **Disclosed:** G2 has already been run during development, with this result:

  | Quantity | Worst relative difference |
  |---|---|
  | py | 3.0e-15 |
  | P | 2.2e-11 |
  | T | 3.7e-14 |
  | DP | 7.9e-13 |
  | Pinv | 1.3e-11 |

  So it is not blind. It stays as a regression check.

**G3. Symplectic check.**

- Criterion: |det DP − 1| ≤ 1e-8 at every G1 and G2 point, for both libraries and MNFlow.
- This is the check that would have caught the bug above directly.

**G4. Long returns (OPEN, for the Bridge).**

- The G1 and G2 points return in T ≈ 700. The homoclinic excursion turns at r ≈ 46.8M, and step 2's later arc
  points take longer returns.
- Proposal:
  - take 10 points from the W^u arcs that the Python B15 already journalled (b15_kerr.journal);
  - compare one return of kerr_rs, kerr_p and the journalled MNFlow value;
  - criterion: ≤ 1e-10 × max(1, T/700), so that integration error growing linearly in T is allowed and nothing else is.
- Question for the Bridge: is linear-in-T the right allowance, or should G4 use the G1 criterion unscaled and, on a
  failure, tighten rtol and atol to 1e-13 (never loosen the criterion)?
- Using the journal reads Python B15 outputs. Those are map values, not step-2 crossings or verdicts. I propose
  that this is acceptable, and the Bridge should check that.

**G5. End-to-end step 1.**

- Run: `find_periodic` from the seed with kerr_rs.
- Criterion: z within 1e-9 of the recorded Python step 1, and λ_u within 1e-8 relative of 62.62026858030255.
  The Python step 1 is already known, so this is a validation, not a prediction.

**On a failure:** fix the implementation, or tighten the tolerances, and rerun the whole gate set. A criterion is
never relaxed (B16 and the rigour rule). A change to a criterion is a new registered amendment, with its reason.

## The run (after the gates)

- Script: b15_kerr_ck.py with the map chosen by an environment variable (B15_MAP=rust). The default stays MNFlow.
- New journal and JSON names, so nothing from the stopped Python run is reused as an output.
- The step-1 result from Python is kept and compared (G5), not reused.
- Resources: one process, with no low-priority nice (the user's instruction for the MN runs). Expected to run in hours,
  not days. There is no wall-time cap (B16).
